# T5 测试方案总览（最终版，2026-10-25）

> 这份文件把整条测试线的**方案、脚本、数据来源、判据演进、结论与撤回**写在一处。
> 目的是：任何人（包括三个月后的自己）读这一份就能知道哪些结论能用、哪些不能用、为什么。

## 一、要回答的问题

**主问题**（来自 #6807）：

> `relative_move.max_step = 127` 有没有实测依据？

这个常量自身的来源链：

```text
#6746 CloudBridge.cpp:368-372 的一行注释（closed、未合并、Codex 辅助）
  → cdp_controller.py:43 抄成 _MAX_RELATIVE_STEP = 127
    → #6696 带着它
      → #6807 准备写成协议默认值 "max_step": 127
```

**派生问题**：

1. 云网页客户端的旋转，是由 `movementX` 驱动，还是由指针**位置差**驱动？
2. `kDefaultTurnUnitsPerDegree = 4.0` 是否成立（即 360 units 是否真的等于 90°）？
3. 连续大角度（如 8×90°）在这个环境里能不能做？
4. 视口边界是不是硬限制？要不要 pointer lock？

## 二、控制器、画面与输入

### 2.1 三条路径要分清

| 路径 | 控制器 | 谁在用 |
| --- | --- | --- |
| **生产路径**（#6696） | `CustomController`（`cdp_controller.py`）→ CDP → Chrome | MXU / 我们自己的 run.py |
| **测量路径**（本套脚本） | **无控制器**，脚本直接连 CDP | 只用于测试 |
| 参考路径（MaaFramework 自带） | `MaaLinuxControlUnit`（Wlr 截图/输入） | 只用于 L1/L0 验证，**与云网页无关** |

本套 T5 脚本**不经过 MaaFramework、不经过任何控制器**，直接用 CDP 与页面对话。
原因是：要排除控制器层的干扰，只看「CDP 事件 → 页面 → SDK」这一段。

### 2.2 画面

| 项 | 值 |
| --- | --- |
| 获取方式 | `Page.captureScreenshot`（PNG，base64） |
| 视口 | 1280×720，`deviceScaleFactor = 1`，与 MaaEnd 的 720p 基准一致 |
| 浏览器 | WSL 内 `google-chrome --kiosk`（或 `--headless=new`），`--remote-debugging-port` |
| 合成器 | 嵌套 sway（WSLg 可见窗口），`WAYLAND_DISPLAY=wayland-1` |
| 渲染 | 软件渲染（无 GPU 直通） |

### 2.3 输入

| 项 | 值 |
| --- | --- |
| 方式 | `Input.dispatchMouseEvent{ type: "mouseMoved", x, y }`，绝对坐标 |
| 锚点 | (640, 360) |
| 相对移动 | 靠两次绝对坐标之差（640 → 640+dx）让浏览器算出位移 |
| 坐标系 | 视口 CSS 像素；x 上限 1279（视口外事件被丢弃） |

## 五、判据演进（八版，两次撤回）

| 版本 | 判据 | 结果 | 是否成立 |
| --- | --- | --- | --- |
| v1 `t5` browser/hook | 探针页读 `movementX` | 60–360 全部精确 | ✅ 成立（只证明浏览器与注入层） |
| v2 `t5b` 角度法 | 箭头前后角度差 | 首步 Δ=0 → 自检拦下 | ✅ 正确拦下（角色不跟镜头） |
| v3 `t5c` 等效性 | 一次发 T vs 拆开，比画面差 | 0.83–1.25× 噪声 → 「无截断」 | ❌ **撤回** |
| v4 `t5d` 标定+时间 | 相位相关求平移；三种发法 | 平移乱跳；三发法差 3.3–4.8× | ❌ 无结论 |
| v5 `t5f` 8×90° | 连续累积后闭环 | 指针出视口即无事件 | ❌ 不可执行 |
| v6 `t5g` + pointer lock | 闭环 + 锁定 | 锁定后 rotation 停止而 movementX 仍 360 | ✅ **成立（关键发现）** |
| v7 `t5h` 丢失检测 | 静止场景下 +T/−T 残差 | 噪声本身 7.4–26.8 不稳 | ⚠️ 待重跑 |
| v8 `t5i` 走一步定角 | 转镜头后走一步，读 rot 变化 | **3.87 units/度、单次上限 ≈126 units** | ✅ **成立（决定性）** |
| v9 `t5j` 生产路径补测 | 固定锚点 + 覆写 movementX，按 127 拆段 | 旧 45.4° / 新 91.9°（名义 90°），与探针对照 89.5° 等价 | ✅ **修正生效** |

### 5.1 v6 的关键发现

pointer lock 下每步 `movementX=360`，但 `clientX` 冻结在 2080：

| 步 | 与起点差 | 与上一步差 |
| --- | --- | --- |
| 1 | 24.02 | 24.02 |
| 2 | 24.49 | 3.60 |
| 3 | 24.62 | 1.47 |
| 6 | 24.68 | 0.49（≈噪声 0.51） |

**第一步转了，之后停止。** 说明客户端按 **`clientX` 位置差** 计算旋转，不读 `movementX`。

### 5.2 这条结论推翻了什么

| 之前 | 现在 |
| --- | --- |
| `max_step=127` 是防 SDK 截断 `movementX` | 前提可能不成立：该客户端似乎不读 `movementX` |
| #6746 用 `defineProperties` 改 movementX 即可转视角 | 在本客户端上不成立，必须真的移动指针位置 |
| v3「一次 360 与 3×120 等效 ⇒ 无截断」 | 两者位置差都是 360，等效是**必然的**，与截断无关 |

### 5.3 v8 决定性数据（t5i）

用「转镜头 → 走一步 → 读 rot 差」测出的曲线（每组 2 次重复，`rot` 稳定 ±1°）：

| 单次 units | Δ（度） | 折算 units/度 |
| --- | --- | --- |
| 60 | 16.5 | 3.64 |
| 90 | 23.4 | 3.85 |
| 100 | 24.0 | 4.16 |
| 120 | 32.3 | 平台 |
| 127 | 33.0 | 平台 |
| 150 | 31.9 | 平台 |
| 180 | 32.6 | 平台 |
| 360 | 32.9 | 平台 |

线性段平均 3.87 units/度；平台平均 32.54° 折算 **125.9 units**。两个数字精确落到
`kDefaultTurnUnitsPerDegree = 4.0` 与 `_MAX_RELATIVE_STEP = 127` 上。

拆段对照（决定性）：

| 360 units 发法 | Δ（度） |
| --- | --- |
| 一次到位 | 32.9 |
| 拆 3×120 | **94.0** |

→ **`max_step` 是必要且正确的**；单次位移超 ~126 units 的部分被丢弃，转大角度必须拆段。

为什么 v3/v4 会错：两者都用「画面差」当判据，而当时场景在动（噪声 7.38–26.8）、
截帧可能在相机平滑移动中；更根本的是判据与「单次上限」无因果关系——位置差总和相同，
截断与否都可能得到相同画面。v8 改用**角度**后，32° 与 94° 一眼可分。

## 七、结论汇总

### 7.1 成立

| 结论 | 依据 | 强度 |
| --- | --- | --- |
| 浏览器与页内注入层不丢 `movementX` | 探针页 40 次采样，60–360 全精确 | 强 |
| 客户端读 **`movementX`**（位置差不变也能转） | T5j：固定锚点 + 覆写 movementX → 91.9° | 强（已修正 T5g 的错判） |
| 箭头是 `rot`（角色朝向），不随镜头 | 实测恒 130.9°/90.8°；文档 `map-locator.md:41-43` 明确 | 强 |
| 箭头读取器精度 1.41°（中位） | 86 张带标注图 | 强 |
| 视口 1280×720 下指针行程上限 639 units/腿 | 1360 起无事件 | 强 |
| 两个 CDP 会话可并发、双向点击无串扰 | t3：延迟 1.1→1.3ms，收到 2 次 | 中 |
| 灵敏度 **3.87 units/度**（协议值 4.0） | 60/90/100 三点线性段 + 拆段 360→94° | 强 |
| 单次事件上限 **≈126 units（≈32°）** | 120/127/150/180/360 全部落在 31.6–33.9° 平台 | 强 |
| 拆段可突破上限 | 360 一次 32.9° vs 拆 3 段 94.0° | 强 |
| Linux 当前 `delta×2` 只转出一半角度 | `controller.go:134` vs 实测 3.87 | 强（结论） |
| pointer lock 可绕开坐标限制但会冻结位置 | x 到 3000 仍派发；clientX 冻在 2080 | 强 |

### 7.2 撤回

| 说法 | 撤回原因 |
| --- | --- |
| 「128–360 units 无截断，`max_step=127` 无必要性」 | 实测存在约 126 units 硬上限；当时判据与截断无因果关系 |
| 「一次 360 与 3×120 等效」 | 只在位置差总和意义成立；实际转角 32.9° vs 94.0°，差 3 倍 |
| 「时间维度无影响」 | v4 三种发法差异 3.3–4.8×，但当时噪声不稳，无法判定 |

### 7.3 阻塞

| 项 | 缺什么 |
| --- | --- |
| 8×90° 连续转向 | 单腿最多 639 units ≈160°；超出必须回位，而回位也受 126 units 限制只能回 ~32°，**残留偏移** |
| 纵向 `dy` / 俯仰 | 未测；`dy = delta × 2` 需单独标定（滑索 `dy = −1500` 仍悬空） |
| JPEG 对识别的影响 | 需 pnpm + 测试集全量 |
| 取帧延迟完整表 | 缺一张真实游戏截图（现有素材是纯色图，脚本会拒绝） |

### 7.4 对 Linux 适配的结论

Go 侧 `controller.go:133-134`：

```go
delta := params.Delta % 360
dx := delta * 2 // 视角旋转灵敏度：1 度偏航对应 2 像素横向拖动
```

`delta` 是**度**，所以当前是 **2 units/度**，而客户端是 **3.87–4.0 units/度**。

> **同一条「转 90°」的命令，Linux 现在只转出 45°。**

应改为 `dx := delta * 4`（取协议值 4.0）。不能全局改——Win32 与 ADB 各有独立标定
（7.93 与 3.0 units/度），必须按控制器类型区分。

`_MAX_RELATIVE_STEP = 127` **必须保留且必须真拆**：90° → 360 units → 3 段 ×120（实测 94°）。

新增约束：

| 约束 | 数值 | 后果 |
| --- | --- | --- |
| 单次上限 | ~126 units / ~32° | 超限丢 delta，必须拆段 |
| 单腿行程 | 639 units / ~160° | 超 160° 必须回位 |
| 回位代价 | 也受 126 上限 | 大步回位只回 ~32°，残留偏移需闭环校正 |

## 八、下一步（按性价比排序）

1. **纵向标定（dy/俯仰）**：`t5i` 的走一步法同样适用，改成「抬头 → 走一步」即可
2. **取帧延迟补测**：只要一张真实游戏截图，就能回答 #6807 标为「决定方案能否成立」的风险 1
3. **对 `max_step` 的正式表述**：不要只写数字，要写清「客户端按 `movementX` 换算旋转，
   单次最多换算约 127 units ≈32°，超出丢弃；因此大角度必须拆段，且受视口行程限制」
4. **纵向标定**：`pitchUnitsPerDegree` 目前与水平共用，属未验证假设
5. 若要绝对镜头角：搭 `camRot`（编译 cpp-algo + 模型 382 KB + 资产）
