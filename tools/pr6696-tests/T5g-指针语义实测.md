# T5g 实测 · 云网页客户端用的是「指针位置差」，不是 movementX

> **⚠️ 本文结论已被 T5j 修正（2026-10-25）。**
> T5j 在生产发法下（指针始终停在 640,360，位置差恒为 0，仅覆写 `movementX`）实测转出 91.9°，
> 证明客户端读的就是 `movementX`。T5g 里旋转停止的真正原因是**指针锁定状态被客户端忽略**，
> 不是「位置差为 0」。下文第三、四节的相关推断作废；仅「pointer lock 不能当解法」仍然成立。
> 现行机制见 `T5j-修正生效补测.md` 第五节。

> 这一轮通过 pointer lock 把视口限制绕开，反而暴露了真正的机制。
> 结论会改变 #6696 的实现判断和 #6807 里 `max_step` 的意义。

## 一、视口限制是什么

不是 CDP 的固有缺陷，是「用绝对坐标合成鼠标事件」的必然结果：

```text
Input.dispatchMouseEvent{ type: "mouseMoved", x, y }   ← x/y 必填
Chrome 在该点做命中测试 → 点在视口外（x ≥ 1280）→ 没有目标元素 → 事件被丢弃
```

实测（视口 1280×720）：

| clientX | 页面收到 | movementX |
| --- | --- | --- |
| 640 | 1 条 | 0 |
| 1000 | 1 条 | 360 |
| **1360** | **0 条** | — |
| 1720 / 2080 | 0 条 | — |

CDP 没有「只发增量」的 API（`dispatchMouseEvent` 必须给坐标），所以单纯推进坐标走不出视口。

## 二、pointer lock 能绕开

`Runtime.evaluate(userGesture=true)` 可以直接请求 `video.requestPointerLock()`（满足用户激活要求）：

```text
请求 document.querySelector('video') → 锁定=True
锁定后：
  x= 640 → 3 条事件  movementX = -1440 / 0
  x=1000 → 3 条事件  movementX = 360
  x=1360 → 3 条事件  movementX = 360
  x=1720 → 3 条事件  movementX = 360
  x=2080 → 3 条事件  movementX = 360
  x=3000 → 3 条事件  movementX = 920
```

**视口外的坐标也能派发**，movementX 按增量精确走。所以「行程受限」这一条被解除了。

## 三、但锁定后画面不再转 —— 这是关键发现

`t5g_loop_closure.py --settle 2.5 --steps 6`（每步 +360 units，pointer lock 已获得）：

噪声基线 **0.51**（场景静止，三帧都是 0.5）

| 步 | clientX | 与起点差 | 与上一步差 |
| --- | --- | --- | --- |
| 1 | 1000 | 24.02（46.7× 噪声） | 24.02 |
| 2 | 1360 | 24.49 | **3.60** |
| 3 | 1720 | 24.62 | **1.47** |
| 4 | 2080 | 24.61 | **1.09** |
| 5 | 2440 | 24.74 | **1.01** |
| 6 | 2800 | 24.68 | **0.49（≈噪声）** |

**第一步转了，之后每步的画面变化迅速收敛到噪声。** 而在锁定状态下 `movementX` 每步都是 360（上表已验）。
同时 `e.clientX` 在锁定时**冻结在 2080**（指针被锁住，位置不再随参数变化）。

结论：**客户端是拿 `clientX` 的位置差算旋转的，不是拿 `movementX`。**
位置冻结 → 位置差为 0 → 不再旋转，尽管 movementX 仍是 360。

## 四、这条结论推翻了什么

| 之前的说法 | 现在 |
| --- | --- |
| 「`_MAX_RELATIVE_STEP = 127` 是为了防止 SDK 截断 movementX」 | **该前提可能不成立**：这个客户端似乎根本不读 movementX |
| 「#6746 用 `Object.defineProperties` 改写 movementX 就能转视角」 | 在这个客户端上**不成立**——必须真的移动指针位置 |
| 「一次发 360 与拆 3×120 等效」（T5c） | 两者位置差都是 360，等效是**必然的**，与截断无关。T5c 的结论因此无效 |
| 「画面差可以当判据」（T5d 的矛盾） | T5d 的矛盾来自运动中截帧与场景动画；静止后噪声只有 0.51，判据本身可用，但**必须静止** |

## 五、对 #6696 / #6807 的实际影响

1. **`relative_move` 必须真实移动指针位置**，且必须保证指针不贴边——
   贴边后位置差为 0，旋转就停。这与 #6696 里 `cursorDX/cursorDY` 累积、超 ¼ 屏复位的做法一致，
   但**复位方式**要重新审视：复位本身会产生反向位置差。
2. **`max_step`（单次上限）这个字段的语义需要重新定义**：
   既然客户端读的是位置差，真正的约束是**指针行程**（视口边界），不是单次幅度。
3. **pointer lock 不是解法**：锁定后位置冻结，反而不转。

## 六、仍然做不到的事

「连续转 8×90°」在位置差语义下依然不可行：
单腿行程 639 units（640→1279），按 4 units/度约 160°，到不了 720°；
每次回位又会产生反向旋转。

要突破，只能改客户端行为（例如它自己支持锁定后读 movementX），这不在我们可控范围内。

## 七、下一步建议

1. 用**静止场景**重做「等量不同拆法」——现在噪声 0.51，判据灵敏度提升了 20 倍，
   之前 T5d 的矛盾有机会澄清
2. 验证「位置差 → 转角」的线性：静止场景下，dx 与画面差的曲线应单调且可分辨
3. `max_step` 的建议改为：**写清「本客户端按指针位置差计算旋转」，单次上限无意义；
   真正要做的是行程管理与复位**——这条对上游比一个数字有用得多
