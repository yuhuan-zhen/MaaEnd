## 3 · 逐段详读

### 段 1 · C API 薄壳层：`Common/MaaController.cpp`

我们调用的每个 `MaaControllerXxx` 都长一个样子。以 `MaaControllerPostConnection` 为例（`MaaController.cpp:57`）：

```c
MaaCtrlId MaaControllerPostConnection(MaaController* ctrl)
{
    LogFunc << VAR_VOIDP(ctrl);

    if (!ctrl) {
        LogError << "handle is null";
        return false;
    }

    return ctrl->post_connection();
}
```

三件事：

1. **`LogFunc`** 是入口日志宏，自动打出函数名与参数 —— `maa.log` 里看到的那一行就是它。
2. **空句柄检查**：`return false`，而返回类型是 `MaaCtrlId`（`int64_t` 的别名）。**`false` 即 `0`**，而 `MaaInvalidId` 就是 0。这就是我们 `l0_env.cpp:81` 判 `job_id == 0` 的依据。
3. **`ctrl->post_connection()`**：`MaaController` 是不透明类型，内部就是 `ControllerAgent`（见 `MaaFramework.cpp:283`）。

整个文件 415 行全是这种 8 行模板，没有业务逻辑。**为什么值得单独一层**：C API 要保证 ABI 稳定，不能把 C++ 类的内存布局暴露出去。

`MaaControllerWait`（`:334`）多一处：

```c
    if (!ctrl) {
        LogError << "handle is null";
        return MaaStatus_Invalid;      // 0，与 MaaStatus_Pending 不同
    }
    return ctrl->wait(id);
```

`MaaStatus_Invalid = 0`，`MaaStatus_Pending = 1000`。所以「返回 0」一定意味着**调用本身就失败了**，不是「还没跑完」。

### 段 2 · 执行器：`ControllerAgent`

#### 2.1 `wait` 是怎么阻塞的（`:190`）

```cpp
MaaStatus ControllerAgent::wait(MaaCtrlId ctrl_id) const
{
    if (!action_runner_) {
        LogError << "action_runner_ is nullptr";
        return MaaStatus_Invalid;
    }
    if (ctrl_id == MaaInvalidId) {
        return MaaStatus_Invalid;
    }

    action_runner_->wait(ctrl_id);
    return status(ctrl_id);
}
```

注意三点：

- `action_runner_` 是另一个对象 —— **ControllerAgent 自己不跑任务**，只做排队与状态查询。
- `wait` 内部是阻塞的（条件变量），所以我们 L0 里 `MaaControllerWait(...) == MaaStatus_Succeeded` 拿到结果时，连接真的完成了。
- 结尾又调 `status()`（`:181`）重新查一次，而不是直接用 `wait` 的返回值 —— 保证读到的是最终态。

#### 2.2 `connected` 是转发（`:204`）

```cpp
bool ControllerAgent::connected() const
{
    if (!control_unit_) {
        return false;
    }
    return control_unit_->connected();
}
```

`control_unit_` 就是插件返回的 `LinuxControlUnitMgr`。所以链路是：

```text
MaaControllerConnected → ControllerAgent::connected → LinuxControlUnitMgr::connected (LinuxControlUnitMgr.cpp:58)
```

后者只是 `return connected_;`，而 `connected_` 在 `connect()`（`:25`）末尾被置真。

#### 2.3 `get_resolution` 读的是缓存（`:232`）

#### 2.4 `MaaControllerDestroy` 为什么能 `delete` 一个 `MaaController*`

`MaaFramework.cpp:341`：

```c
void MaaControllerDestroy(MaaController* ctrl)
{
    LogFunc << VAR_VOIDP(ctrl);
    if (!ctrl) {
        return;
    }
    delete ctrl;
}
```

`MaaController` 在 `MaaDef.h` 里是 `struct MaaController;` 的**不完全类型**，但 `ControllerAgent` 继承它并声明了**虚析构**（`ControllerAgent.h`）。所以 `delete` 走虚函数表，正确析构派生类。

这就是我们的 `ScopedController::~ScopedController`（`l0_env.cpp:46-51`）能安全调 `MaaControllerDestroy` 的底层保证：不是「应该没问题」，而是有虚析构兜底。

### 段 3 · 库加载器与自定义 deleter：`ControlUnit.cpp:365`

`MaaLinuxControllerCreate`（`MaaFramework.cpp:286`）的正文：

```cpp

    if (!control_unit) {
        LogError << "Failed to create control unit";
        ...
```

两件事：**平台宏**（非 Linux 编译时函数体只剩返回 `nullptr`）与**库加载器**。

加载器本体（`ControlUnit.cpp:365`）逐句读：

```cpp
std::shared_ptr<MAA_CTRL_UNIT_NS::LinuxControlUnitAPI> LinuxControlUnitLibraryHolder::create_control_unit(const char* config_json)
{
    if (!load_library(library_dir() / libname_)) {          // ① dlopen libMaaLinuxControlUnit.so
        LogError << "Failed to load library" << VAR(library_dir()) << VAR(libname_);
        return nullptr;
    }

    check_version<LinuxControlUnitLibraryHolder, decltype(MaaLinuxControlUnitGetVersion)>(version_func_name_);  // ② 版本校验

    auto create_control_unit_func = get_function<decltype(MaaLinuxControlUnitCreate)>(create_func_name_);        // ③ dlsym
    if (!create_control_unit_func) { ... }

    auto destroy_control_unit_func = get_function<decltype(MaaLinuxControlUnitDestroy)>(destroy_func_name_);     // ④ 取销毁函数
    if (!destroy_control_unit_func) { ... }

    auto control_unit_handle = create_control_unit_func(config_json);                                            // ⑤ 造对象

    if (!control_unit_handle) { ... }

    return std::shared_ptr<MAA_CTRL_UNIT_NS::LinuxControlUnitAPI>(control_unit_handle, destroy_control_unit_func);   // ⑥
}
```

四个要点：

| # | 细节 | 为什么 |
| --- | --- | --- |
| ① | `load_library(library_dir() / libname_)` | 用**显式路径** dlopen，不靠 `LD_LIBRARY_PATH` 猜 |
| ② | `check_version` | 框架与插件可能来自不同版本安装包，版本不符会明确报错而不是崩溃 |
| ③④ | `get_function` = `dlsym` | C ABI 函数的运行期绑定 |
| ⑥ | `shared_ptr(handle, destroy_func)` | **自定义 deleter**：句柄不是 `new` 出来的，不能用 `delete`；必须调插件的销毁函数 |

第 ⑥ 点是整个设计里最巧的一处：`shared_ptr` 的第二个参数接受任意可调用物作为销毁器，于是**插件的生命周期被 std 智能指针管理**，框架侧不需要额外记账。

我们 L0 的 `ScopedController` 是这条思路的手写简化版：`l0_env.cpp:46` 的析构函数调 `MaaControllerDestroy`。区别是 `shared_ptr` 用引用计数（可共享），我们用栈作用域（单所有者）。

### 段 4 · 插件入口：`LinuxControlUnitAPI.cpp:14`

只剩 49 行的文件里，核心是：

```c
MaaLinuxControlUnitHandle MaaLinuxControlUnitCreate(const char* config_json)
```

它把 JSON 字符串解析成 `LinuxControlUnitMgr::Config`，失败返回 `nullptr`。**注意命名层次**：这个函数名带 `LinuxControlUnit` 而不是 `Controller` —— 它是**插件导出符号**，不是给用户调用的 API。用户态入口只有 `MaaLinuxControllerCreate` 一个。

### 段 5 · 真正的实现：`LinuxControlUnitMgr`

#### 5.1 `connect`（`:25`）

```cpp

    screencap_.reset();
    input_.reset();
```

**先清空、再按配置重建**。Wlr 的截图或输入任一被选中，就必须先建 `WaylandClient`（因为两者共享同一条 wayland 连接）。

顺序也重要：`create_wl_client` → `create_screencap` → `create_input`。截图在输入前，因为输入可能依赖截图得到的尺寸。

#### 5.2 `get_features`（`:99`）

```cpp
MaaControllerFeature LinuxControlUnitMgr::get_features() const
{
    MaaControllerFeature feat = MaaControllerFeature_None;
    if (input_) {
        feat |= input_->get_features()
                & (MaaControllerFeature_UseMouseDownAndUpInsteadOfClick | MaaControllerFeature_UseKeyboardDownAndUpInsteadOfClick);
    }
    return feat;
}
```

两个细节：

- 用 `&` 做**白名单过滤**：只放行两位置信位，input 返回的其它位一律丢掉。防止插件声称一些框架不认识的能力。
- `input_` 为空时返回 `None` —— 所以 `connect()` 之前调用是安全的。

#### 5.3 位标志被谁消费（`ControllerAgent.cpp:457`、`:789`）

`get_features` 只是「声明」，真正的分岔在执行器里。点击（`:457`）：


### 段 6 · Wayland 与接口契约

#### 6.1 `WaylandClient::open`（`WaylandClient.cpp:32`）

```cpp
    display_.reset(wl_display_connect(socket_path_.c_str()));
```

一行。`socket_path_` 就是我们 `config_json` 里的 `wlr_socket_path`。

**这解释了为什么 socket 路径写错会直接连接失败**：`wl_display_connect` 返回 `nullptr`，`open()` 失败，`connect()` 返回 false，`connected` 永远是 false。整条链路没有「重试」也没有「自动猜路径」。

#### 6.2 接口契约（`UnitBase.h`）

三个抽象基类定义了「一个控制单元最少要实现什么」：

| 类 | 行 | 必实现的纯虚函数 | 作用 |
| --- | --- | --- | --- |
| `ScreencapBase` | `:20` | `screencap(cv::Mat&)` | 抓一帧 |
| `InputBase` | `:33` | `get_features` / `click` / `swipe` / `touch_*` / `click_key` / `input_text` / `key_down` / `key_up` / `scroll` | 全部输入 |
| `RelativeMoveInput` | `:61` | `relative_move` | 可选能力 |

注意 `init()` 与 `inactive()` 都有**默认空实现**（`:26`、`:30`、`:58`），所以子类可以只关心自己需要的。这是「宽接口 + 默认实现」的典型用法，也是为什么 `InputBase` 有 10 个纯虚函数却不会逼着每个平台都写满 —— 不支持的返回 false 即可。

## 4 · 四处「原来如此」

### ① `get_resolution` 不是没实现，是**还没值**（旧结论作废）

我之前在 `docs/01` 和 `study/L0-详读.md` 里写的是「Linux 控制器未实现该 API」——**这个结论是错的**，源码对照推翻了它。

真相（`ControllerAgent.cpp:232` + `:1253`）：

```cpp
bool ControllerAgent::get_resolution(int32_t& width, int32_t& height) const
{
    if (image_raw_width_ == 0 || image_raw_height_ == 0) {
        return false;                     // ← 只是"还没有值"
    }
    ...
```

而 `image_raw_width_` 只在**截图成功之后**才被赋值（`:1253`，位于截图流水线内）：

```cpp
    if (raw.cols != image_raw_width_ || raw.rows != image_raw_height_ || image_target_width_ == 0 || image_target_height_ == 0) {
        LogInfo << "Resolution changed" << VAR(raw.cols) << VAR(raw.rows) << VAR(image_raw_width_) << VAR(image_raw_height_);

        image_raw_width_ = raw.cols;
        image_raw_height_ = raw.rows;
```

所以：

| 时刻 | `get_resolution` | 原因 |
| --- | --- | --- |
| `connect()` 之后、未截图 | **false** | `image_raw_*` 还是 0 |
| 成功 `screencap` 一次之后 | **true，返回真实尺寸** | 缓存已填 |

**结论**：`MaaControllerGetResolution` 在 Linux 上是可用的，只是**必须先截一帧**。

已验证（2026-10-25，嵌套 sway，socket `wayland-1`，maafw Python binding v5.14.3）：

```text
connect job: True
resolution BEFORE screencap: (0, 0)
screencap shape:             (720, 1280, 3)
resolution AFTER  screencap: (1280, 720)
```

复现脚本（**工具范畴，Python**：这段只为一行验证上游语义，主线实现是 C++，见 [`PLAN.md`](../PLAN.md) 的「语言规范」；L1 的 C++ 版会给出等价验证）：

```bash
python3 - <<'PY'
from maa.controller import LinuxController
from maa.define import MaaLinuxScreencapMethodEnum as SC, MaaLinuxInputMethodEnum as IN
c = LinuxController({"screencap_method": SC.Wlr, "input_method": IN.Wlr,
                     "wlr_socket_path": "/run/user/0/wayland-1"})
print("connect:", c.post_connection().wait().succeeded)
print("before:", c.resolution)
img = c.post_screencap().wait().get()
print("frame:", img.shape)
print("after :", c.resolution)
PY
```

它还有一个隐含用途：判断「分辨率是否变化」—— `raw.cols != image_raw_width_` 那个条件就是变更检测，变化时会重算缩放尺寸（`calc_target_image_size`，`:1268`）。

### ② `MaaCtrlId` 的 0 就是失败

`MaaControllerPostConnection` 在空句柄时 `return false`，而返回类型是 `MaaCtrlId`。`MaaInvalidId == 0`。所以「`job_id == 0` 判失败」是框架自身也遵守的约定，不是我们的猜测。

### ③ feature 位在**执行器**消费，不在插件里

`get_features` 只是申报。真正的分岔在 `ControllerAgent::handle_click`（`:457`）与 `handle_key`（`:789`），并且**框架会替你插入 50 ms 的按住时长**。所以插件报 `UseMouseDownAndUpInsteadOfClick` 不需要自己睡 50 ms。

### ④ `shared_ptr` 的第二个参数是销毁器

`ControlUnit.cpp:365` 末尾：

```cpp
    return std::shared_ptr<MAA_CTRL_UNIT_NS::LinuxControlUnitAPI>(control_unit_handle, destroy_control_unit_func);
```

`control_unit_handle` 是裸指针，但不是 `new` 出来的（它来自插件内部的工厂），所以不能 `delete`。把插件的 `destroy` 函数当销毁器传进去，就得到「引用计数 + 正确销毁」的组合。

## 7 · 自测 6 题

1. `MaaControllerPostConnection` 在 `ctrl` 为空时返回什么？这个值为什么能当「失败」判断？
2. `MaaControllerGetResolution` 在 Linux 上返回 false 的**真实原因**是什么？什么时候会开始返回 true？
3. `get_features` 返回的位，是插件自己用，还是框架用？在哪一行被消费？
4. `LinuxControlUnitLibraryHolder::create_control_unit` 返回的 `shared_ptr` 为什么必须传第二个参数？
5. `start_app` 返回 false 与 `get_resolution` 返回 false，性质有什么不同？
6. `MaaLinuxControllerCreate` 在非 Linux 平台上编译出来是什么行为？

<details>
<summary>答案</summary>

1. 返回 `false`，即 0；`MaaInvalidId` 就是 0。框架自己也用 0 表示无效 id。
2. 因为 `image_raw_width_/height_` 为 0，它们只在截图成功后（`ControllerAgent.cpp:1253`）才被赋值。成功截一帧之后就会返回真实尺寸。
3. 框架用。在 `ControllerAgent::handle_click`（`:457`）与 `handle_key`（`:789`）里分岔成 `touch_down+50ms+up` 或 `click`。
4. 因为句柄不是 `new` 出来的，不能 `delete`，必须调插件导出的 `MaaLinuxControlUnitDestroy`。
5. `get_resolution` 是「暂时没有值」（截一帧就有）；`start_app` 是「函数体只有 TODO，永远返回 false」。
6. 函数体只剩 `LogError << "This API ... is only available on Linux"; return nullptr;`，其余被 `#ifndef __linux__` 排除。

</details>
