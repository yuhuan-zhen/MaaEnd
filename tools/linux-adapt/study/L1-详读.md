# L1 详读：从「连上」到「拿到这一帧的像素」

对象：`mini-cpp/l1_screencap.cpp`（342 行，clang-format 零改动）。
注释版：`mini-cpp/l1_screencap_annotated.cpp`（442 行，预处理后 md5 与原文一致）。

## 0 · 这一层要证明什么

| # | 判据 | 实测（2026-10-25） |
| --- | --- | --- |
| 1 | 抓到一帧，尺寸/通道/类型正确 | `1280x720, channels = 3, type = 16` |
| 2 | 通道序是 **BGR** 而不是 RGB | 背景 `#1b2b34` → 均值 `[52, 43, 27]`（B>G>R）✅ |
| 3 | `GetResolution` 截过一帧后有值 | `resolution = 1280x720`（L0 里是 false）✅ |
| 4 | 单帧耗时量级 | median **16.14 ms**，min 4.25，p95 16.60 |

第 2 条是全篇的关键设计：**用合成器背景色当标尺**。`#1b2b34` 的 R=27 / G=43 / B=52，如果读到 `[52,43,27]` 说明字节序是 B,G,R；读到 `[27,43,52]` 就是 R,G,B。不需要 grim、不需要对比图，一个数字就定案。

## 1 · 与 L0 的差别

| | L0 | L1 |
| --- | --- | --- |
| 动作 | create → connect → 查询 | create → connect → **抓帧** → 存盘 → 计时 |
| 新增句柄 | — | `MaaImageBuffer*`（必须 Destroy） |
| 新增概念 | 异步任务 | **视图 vs 拷贝**、通道步长、类型编号 |
| 画面变化 | 无 | **有**：PNG 可以打开看 |

## 2 · 五个概念

### ① 异步任务模型：post → wait → 取结果

```text
MaaControllerPostScreencap(ctrl)   →  返回 job id（立刻返回，任务在框架线程里排队）
MaaControllerWait(ctrl, job_id)    →  阻塞到结束，返回最终状态（3000 = Succeeded）
MaaControllerCachedImage(ctrl, buf)→  把结果拷进你的 buffer
```

**为什么不是「一个函数直接返回图」**：截图是 IO，框架不想让调用方线程模型受它约束。所以「提交」和「取结果」分开，中间用 id 关联。代价是：**你必须自己把两步接起来**，忘了 `CachedImage` 就永远拿不到像素。

### ② buffer 与 view：谁拥有像素

```text
MaaImageBuffer（框架分配，我们 Destroy）
   └── 像素内存（BGR 交错，1280*720*3 = 2,764,800 字节）
         ↑
    ImageView.data 只记指针，不持有
```

`to_view()` 返回的是**结构体拷贝**，但里面的 `data` 仍指向 buffer 内部。所以：

- buffer 活着 → 随便读
- buffer 析构 → `view.data` 悬空，再读就是未定义行为

MaaEnd 的 `utils.h` 里 `to_mat()` 是同一件事（返回 `cv::Mat`，共享 buffer 的像素）。它把这条写在 `ScopedImageBuffer` 的注释里，我们这里用 `ImageView` 表达了同样的契约。

### ③ 类型编号：`type = 16` 是什么

OpenCV 的类型编码规则：

```text
type = depth + ((channels - 1) << 3)
CV_8U = 0  →  CV_8UC3 = 0 + ((3-1) << 3) = 16
```

所以 `type = 16` 就是「8 位无符号 × 3 通道」。它和 `channels = 3` 是冗余的，但两个都打印出来能交叉验证。

### ④ 交错布局与步长寻址

像素不是「先存所有 B，再存所有 G」，而是每个像素三个字节连着：

```text
B0 G0 R0  B1 G1 R1  B2 G2 R2 ...
```

取第 i 个像素的通道 c：

```cpp
offset = i * channels + c
```

代码里 `view.data[i * view.channels + channel]` 就是这一个式子。写错成 `i + c * pixel_count` 会得到“平面布局”的结果——图会变成三条色带，这是很典型的 bug。

### ⑤ PNG 从哪来：框架帮你编码

`MaaImageBufferGetEncoded()` 返回的是 **PNG 字节流**，`GetEncodedSize()` 给长度，直接 `fwrite` 就是一张合法的 PNG。

实测证据：

| 项 | 值 |
| --- | --- |
| 原始像素 | 1280×720×3 = **2,764,800** 字节 |
| PNG 文件 | 5,212 字节（纯色，压缩率极高） |
| 文件头 | `89 50 4e 47 0d 0a 1a 0a`（PNG 签名） |

**所以 L1 不需要 OpenCV**。这一点与 L0 的语言规范一致：主线不引入新依赖。

## 3 · 分块讲解

### 块 1 · 两个 RAII 壳（第 43–95 行）

`ScopedController` 与 `ScopedImageBuffer` 结构完全相同，只换了句柄类型与销毁函数。**没有抽模板**是刻意的：两个类各自独立可读，模板会把「谁负责 Destroy 什么」藏起来。等出现第三、第四个句柄（`MaaTasker` / `MaaResource`）时再考虑模板。

### 块 2 · ImageView 与 to_view（第 97–126 行）

`ImageView` 只有五个字段：`data / width / height / channels / type`。`to_view()` 一次把四个 C API 读完（`GetRawData / Width / Height / Channels / Type`）。这五个调用都**不拷贝像素**，只是读元数据 —— 所以它便宜。

### 块 3 · 通道均值（第 128–145 行）

```cpp
sum += view.data[i * channels + channel];
```

用 `uint64_t` 累加：921,600 像素 × 255 ≈ 2.35 亿，`uint32` 也够，但用更宽的类型可以不用思考溢出。

### 块 4 · 存 PNG（第 147–173 行）

四个检查一个都不能少：

| 检查 | 少了会怎样 |
| --- | --- |
| `encoded == nullptr` | 空指针写文件 → 崩 |
| `size == 0` | 写出 0 字节文件，后面打开才发现是坏的 |
| `fopen` 返回空 | 路径不可写（目录不存在）→ 崩 |
| `written != size` | 磁盘满时静默成功，文件残缺 |

### 块 5 · `grab_once`（第 203–227 行）

一个函数把「post → wait → cached image」三步封在一起，并把计时包在外层。返回 `-1` 表示失败 —— 比传引用出参简单，调用方 `if (cost < 0) return 1;` 一行搞定。

**计时边界很重要**：`begin` 在 `PostScreencap` 之前，`end` 在 `CachedImage` 之后。这样量到的是「提交 + 等待 + 拷贝」的端到端成本，正是使用者关心的那个数。

### 块 6 · 统计（第 229–238 行）

```cpp
std::sort(values.begin(), values.end());
const size_t index = ratio * (size - 1);
```

20 个样本用 `std::sort` 足够。`ratio = 0.95` 时取第 18 个（0-indexed），是「p95」的简化定义（不做插值）。样本少时这个定义足够，不要拿它当严格的统计分位数。

### 块 7 · 参数解析（第 240–263 行）

`--out` / `--frames` / 其余位置参数当 socket。**默认值全部可用**，所以 `./l1_screencap` 不带参数就能跑 —— 验收脚本依赖这一点。

### 块 8 · main 的五段（第 267–342 行）

| 段 | 行 | 作用 |
| --- | --- | --- |
| 建 + 连 | 271–283 | 与 L0 相同 |
| 建 buffer | 285–289 | 空 buffer 也能创建成功，失败只可能是内部错误 |
| 抓第一帧 | 292–310 | 打形状、通道均值、存 PNG |
| 查分辨率 | 312–320 | 验证「截图后才有的值」 |
| 多帧计时 | 322–339 | median / p95 |

## 5 · 源码对照（上游实现，锁 `0fc6025c`）

调用链：

```text
MaaControllerPostScreencap        Common/MaaController.cpp:298
  → ControllerAgent::post_screencap
    → LinuxControlUnitMgr::screencap          LinuxControlUnitMgr.cpp:125
      → WlrScreencap::screencap               WlrScreencap.cpp:11
        → zwlr_screencopy_manager_v1_capture_output   (wlr-screencopy 协议)
        → frame_listener.buffer → create_buffer / copy   第 19–33 行
        → frame_listener.ready → 置 capture_successful_  第 34–40 行

MaaControllerCachedImage          Common/MaaController.cpp:335
  → ControllerAgent::cached_image             ControllerAgent.cpp:213
    → 返回 image_ 的**克隆**（加锁）           ← 这里做了拷贝！

MaaImageBufferGetRawData          Common/MaaBuffer.cpp:208
  → handle->raw_data()

MaaImageBufferGetEncoded          Common/MaaBuffer.cpp:285
  → handle->encoded()                         ← PNG 编码在这里发生

分辨率缓存被填的时机：
  ControllerAgent.cpp:1253   image_raw_width_ = raw.cols;   ← 截图流水线内
```

三条值得记住的结论：

1. **`CachedImage` 是克隆**（`ControllerAgent.cpp:213` 的 `image_.clone()` 加锁保护），所以我们拿到的 buffer 与框架内部那一帧是两块内存 —— 后续再截图不会改掉我们手里的像素。
2. **`image_raw_width_` 在截图流水线里赋值**（`:1253`），这就是 L0 里 `GetResolution` 返回 false、L1 里能返回 `1280x720` 的全部原因。
3. **PNG 编码发生在 `encoded()`**（`MaaBuffer.cpp:285` → MaaUtils 内部 `imencode`）。我们只负责写文件。

## 6 · 与 MaaEnd 的对应

| MaaEnd（`agent/cpp-algo/source/utils.h`） | 本文件 | 差异 |
| --- | --- | --- |
| `ScopedImageBuffer` | `ScopedImageBuffer` | 结构相同；MaaEnd 已抽公共头，我们留在单文件里 |
| `to_mat()` → `cv::Mat` | `to_view()` → `ImageView` | 都不拷贝；MaaEnd 借 OpenCV 的类型，我们自建结构体 |
| `MaaNS::imwrite`（走 MaaUtils） | `MaaImageBufferGetEncoded` + `fwrite` | 目的一样，路径不同；MaaEnd 有 MaaUtils 的 UTF-8 路径处理 |

**为什么不全照抄 `to_mat`**：`to_mat` 需要 OpenCV 头文件，而 SDK release 包里不带 OpenCV，装 `libopencv-*-dev` 要拉 69 个包。为了讲清「视图」这一课，不值得引入这套依赖。等 L3 以后真需要模板匹配时再装。

## 7 · 实测数据（2026-10-25，嵌套 sway 1280×720）

| 项 | 值 |
| --- | --- |
| connect | 与 L0 同（约 200 ms） |
| 第一帧耗时 | 10.2 – 13.6 ms |
| 20 帧 min / median / p95 / max | 4.25 / **16.14** / 16.60 / 16.63 ms |
| 通道均值（背景 `#1b2b34`） | `[52.000, 43.000, 27.000]`（BGR） |
| 换背景为 `#c81e1e` 后 | `[30.000, 30.000, 200.000]`（BGR）→ 证明是实时帧 |
| PNG 体积 | 5,212 B（`#1b2b34`）/ 5,031 B（`#c81e1e`） |
| 原始像素体积 | 2,764,800 B |
| `GetResolution` | `1280x720`（截图后） |

与 `docs/05` 里 Python 线的 16.2 ms 中位一致 —— 说明 C++ 与 Python 走的是同一条链路，语言不是瓶颈。

## 8 · 自测 6 题

1. `MaaControllerCachedImage` 拿到的是「刚抓的那帧」还是「内存里最后一帧」？两者在什么情况下会不同？
2. `type = 16` 怎么算出来的？
3. 为什么 `ImageView` 用完必须保证 buffer 还活着？MaaEnd 里对应的东西叫什么？
4. 存 PNG 为什么要检查 `written != size`？
5. `GetResolution` 在 L0 返回 false、L1 返回 `1280x720`，差别的原因在源码哪一行？
6. 如果通道均值打出 `[27, 43, 52]`，说明什么？

<details>
<summary>答案</summary>

1. 是内存里最后一帧。若跳过了 `PostScreencap` 直接调它，会拿到旧帧 —— `docs/03` 里有这条坑。
2. `CV_8U=0`，`type = depth + ((channels-1) << 3)` = `0 + (2 << 3)` = 16。
3. 因为 `data` 指向 buffer 内部像素，buffer 一销毁就悬空；MaaEnd 里对应 `to_mat()`，它返回的 `cv::Mat` 同样共享像素。
4. 磁盘满或写入被截断时 `fwrite` 会短写，不检查就会把残缺文件当成功。
5. `ControllerAgent.cpp:1253` 的 `image_raw_width_ = raw.cols;` —— 只有截图流水线才会填这个缓存。
6. 说明字节序是 R,G,B（RGB），而不是 BGR —— 那 `screencap_method` 或上游实现出了变化。

</details>
