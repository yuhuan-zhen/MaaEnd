# L0 详读：一个 132 行的程序，讲清 C API 的三条规矩

对象：`mini-cpp/l0_env.cpp`（132 行）；注释版 `mini-cpp/l0_env_annotated.cpp`（216 行，预处理后 md5 与原文一致）。

## 这一层要回答什么

**「我的 C++ 程序能不能跟 MaaFramework 说上话？」**

不截图、不点击、不跑任务。只做四件事：

```text
创建控制器  →  连接  →  查状态  →  销毁
```

为什么先做这个：链接错、头文件版本不对、运行期找不到 `.so`——这三个问题在任何真实功能里都会表现成「莫名失败」。先用 60 行把它们暴露出来，后面 L1~L5 的报错才有意义。

## 三个必懂的概念

### ① handle（句柄）：你不拥有对象，只拥有访问权

C API 不把对象结构暴露出来，只给你一个不透明指针 `MaaController*`。你看不见里面有什么，只能拿它调函数。

推论有两条：

- **谁创建谁销毁**：`MaaLinuxControllerCreate` 配 `MaaControllerDestroy`，忘了就是泄漏
- **不能拷贝**：两个变量指向同一个句柄，销毁两次 = 未定义行为

这就是为什么代码里要包一层 `ScopedController`。

### ② RAII：让析构函数替你收尾

```cpp
class ScopedController
{
public:
    explicit ScopedController(MaaController* handle) : handle_(handle) {}
    ~ScopedController() { if (handle_ != nullptr) MaaControllerDestroy(handle_); }
    ScopedController(const ScopedController&) = delete;            // 禁拷贝
    ScopedController& operator=(const ScopedController&) = delete; // 禁赋值
    MaaController* get() const { return handle_; }
    explicit operator bool() const { return handle_ != nullptr; }
private:
    MaaController* handle_ = nullptr;
};
```

四个细节都有原因：

| 写法 | 为什么 |
| --- | --- |
| `explicit` 构造 | 防止 `void f(ScopedController)` 被 `f(raw_ptr)` 隐式建出临时对象，出来就销毁 |
| `= delete` 拷贝 | 防 double free |
| 析构里判空 | `Create` 失败返回 `nullptr`，把 `nullptr` 传给 `Destroy` 是未定义行为 |
| `explicit operator bool` | 让 `if (!controller)` 合法，同时防止它被隐式当整数用 |

对应 `cpp-algo-style` 的「缓冲区 create/destroy 配对」一条：那边的做法是 `ScopedImageBuffer`，这里同构。

### ③ 异步三件套：Post → Wait → Status

MaaFramework 所有耗时操作都是异步的：

```cpp
const MaaCtrlId job_id = MaaControllerPostConnection(controller);  // 提交，立刻返回编号
const MaaStatus status = MaaControllerWait(controller, job_id);    // 阻塞到结束
if (status != MaaStatus_Succeeded) { /* 失败 */ }                   // 3000 才是成功
```

`MaaStatus` 是 `int32_t`，取值：`1000` Pending、`2000` Running、`3000` Succeeded、`4000` Failed。

**最常见的错误是「Post 完就查状态」**——那时还是 Pending，你会以为操作失败了。必须 `Wait`。

## 分块讲解

### 块 1 · 为什么只 include 一个头（第 22 行）

```cpp
#include <MaaFramework/MaaAPI.h>
```

`MaaAPI.h` 是聚合头，它自己 include 了：

```text
MaaDef.h（枚举与 typedef）
Global/MaaGlobal.h
Instance/{MaaContext, MaaController, MaaCustomController, MaaResource, MaaTasker}.h
Utility/{MaaBuffer, MaaUtility}.h
```

所以不需要逐个引。反过来，如果你只想要枚举值（不调函数），引 `MaaDef.h` 就够，编译更快。

### 块 2 · 那两个 `1` 是什么（第 40、43 行）

```cpp
constexpr int kScreencapMethodWlr = 1;
constexpr int kInputMethodWlr = 1;
```

它们是 C 枚举的整数值，出处是 `[FW-2.4]` 的两张表：

| 枚举 | 值 | 含义 |
| --- | --- | --- |
| `MaaLinuxScreencapMethod` | 1 / 4 | Wlr（screencopy）/ PipeWire |
| `MaaLinuxInputMethod` | 1 / 2 / 4 | Wlr / UInput / Libei |

**写错的后果**：不会报错。传 `4` 会被当成 PipeWire 截图，然后因为找不到 portal 而失败——错误信息和「路径写错」长得一模一样。所以这两个数字要常数化，不要散在代码里。

### 块 3 · JSON 是唯一的配置入口（第 88–100 行）

C API 不收结构体，只收 JSON 字符串：

```cpp
MaaController* MaaLinuxControllerCreate(const char* config_json);
```

必填两项：`screencap_method`、`input_method`。Wlr 还要 `wlr_socket_path`。

我们多写了一个 `use_win32_vk_code: true`——它不是必填，但**不写默认 false**，会让上层传来的 `27`（Esc）被当成 evdev 扫描码，按键全部错位。MaaEnd 的 pipeline 全部按 Win32 VK 写，所以必须显式开。

### 块 4 · main 的四个动作（第 125–214 行）

```text
1. 打版本      MaaVersion()                        ← 证明「头文件对 + 链接通」
2. 拼配置      略
3. 建 + 连     Create → PostConnection → Wait      ← 证明「config 合法 + 能连合成器」
4. 查 + 销毁   GetResolution / Connected，析构自动 Destroy
```

`GetResolution` 在 Linux 控制器上返回 `0x0`（API 未实现），这里**只记录不当失败**——把它当失败会让你误判环境。

## 函数索引

| 函数 | 作用 | 参数 | 返回 | 谁调用 | 注意点 |
| --- | --- | --- | --- | --- | --- |
| `MaaVersion()` | 框架版本 | 无 | `const char*` | `main` | 可能为 null，判一下 |
| `MaaLinuxControllerCreate(json)` | 建 Linux 控制器 | config JSON | `MaaController*`，失败 `nullptr` | `main` | 只建对象，不连接 |
| `MaaControllerPostConnection(ctrl)` | 提交连接任务 | 控制器 | `MaaCtrlId`（0 = 提交失败） | `connect_controller` | 只是提交 |
| `MaaControllerWait(ctrl, id)` | 等待任务结束 | 控制器、id | `MaaStatus` | `connect_controller` | 阻塞，必须调 |
| `MaaControllerConnected(ctrl)` | 查当前连接状态 | 控制器 | `MaaBool` | `main` | 同步查询，非异步 |
| `MaaControllerGetResolution(ctrl, &w, &h)` | 取出分辨率 | 两个出参 | `MaaBool` | `main` | Linux 上返回 0x0 |
| `MaaControllerDestroy(ctrl)` | 销毁句柄 | 控制器 | 无 | `~ScopedController` | 不能重复调 |

## 自测 6 题

1. 为什么 `ScopedController` 要 `= delete` 拷贝构造？
2. `MaaControllerWait` 不调用会发生什么？
3. 把 `kScreencapMethodWlr` 改成 `4` 会怎样？错误信息长什么样？
4. `use_win32_vk_code` 不写会有什么后果？为什么它默认是 false？
5. `GetResolution` 返回 `0x0`，能不能当作「环境有问题」的证据？
6. 退出码为什么要分 `0 / 1 / 2` 三种？

<details>
<summary>答案</summary>

1. 两个对象持有同一句柄会 double free；C API 的句柄没有引用计数。
2. 立刻查状态只会拿到 Pending（1000），你会误判为失败；必须 `Wait` 才拿到终态。
3. 会被当成 PipeWire 截图方式，因找不到 portal 而连接失败；错误信息与「socket 路径写错」相似，很难定位。这正是把枚举值常数化的理由。
4. 上层传入的 Win32 VK（如 27 = Esc）会被当成 evdev 扫描码解释，导致按键全部错位；框架不会报错。
5. 不能。Linux 控制器的 `MaaControllerGetResolution` 尚未实现，返回 0x0 是已知行为，与连接是否成功无关。
6. `1` = 参数/环境错误（建不出来），`2` = 建出来了但连不上；区分它们能立刻定位是「配错」还是「合成器没起」。

</details>

## 这一层的卡点清单

| 卡点 | 判据 | 下一步 |
| --- | --- | --- |
| 编译器缺失 | `which g++ cmake` 为空 | 装 `build-essential cmake`，或用 Windows 侧 MinGW 先做语法检查 |
| `find_package` 失败 | CMake 报 `MaaFrameworkConfig.cmake` 找不到 | 检查 `MAAFW_SDK_DIR/share/cmake` 是否存在 |
| 运行期找不到 `.so` | `error while loading shared libraries` | RPATH 或 `LD_LIBRARY_PATH=/opt/maafw/extract/bin` |
| ControlUnit 加载失败 | `Create` 返回 nullptr | `libMaaLinuxControlUnit.so` 必须在动态链接器搜索路径里 |
| 连不上 | `status = 4000` | socket 路径 / 合成器是否在跑 |
