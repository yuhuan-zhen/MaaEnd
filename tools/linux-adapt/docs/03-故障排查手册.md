# Linux 控制器故障排查手册

面向「动作返回成功但没效果」这类静默故障。每条给判据与定位命令。

## 出事先固定三件事

```bash
# 1. 你的控制器实际是什么类型、连的是哪个 socket
#    MaaControllerGetInfo 在 Python binding 里是 controller.info
python3 -c "import json;from maa.controller import LinuxController;c=LinuxController({'screencap_method':1,'input_method':1,'wlr_socket_path':'/run/user/1000/wayland-0'});c.post_connection().wait();print(c.info)"

# 2. 合成器进程与 socket 是否对得上
ls -l /run/user/$UID/wayland-*
pgrep -a sway   # 或 kwin_wayland / hyprland / gamescope

# 3. 版本
#    MaaFramework: 看 release tag
python3 -c "import importlib.metadata as m;print(m.version('maafw'))"
```

三者不一致时，后面所有排查都会浪费。

## 症状 → 判据 → 定位

### 点击没反应

| 步骤 | 命令 / 判据 |
| --- | --- |
| ① 确认页面真的收到了事件 | 在页面里挂监听：`window.__e=[];addEventListener('pointerdown',e=>__e.push(['down',e.clientX,e.clientY,e.button]))`，动作后读 `__e` |
| ② 事件到了但坐标不对 | 读到的 `clientX/clientY` 与下发值不符 → 检查 `display_*` 缩放与 CSS 尺寸 |
| ③ 完全没有事件 | 先确认下方「画面」一节正常（截图有内容说明渲染在跑） |
| ④ 有事件但游戏没反应 | 大概率是焦点/窗口未激活，或页面用 `requestPointerLock` 抢了指针 |

**最常见原因**：调用方没读 feature 位，直接调 `click()`。`maafw.log` 里会出现 `deprecated: get_features() returns MaaControllerFeature_UseMouseDownAndUpInsteadOfClick`。

### 拖动没反应 / 拖到一半停了

| 判据 | 含义 |
| --- | --- |
| 起点坐标 + 位移越界（`x+dx > 1279`） | 绝对移动被钳制，后半段静默丢失 |
| 连续多次同向拖动后开始无效 | 指针贴边，需要复位（见 [02](02-Wlroots输入链路解剖.md#指针累积与复位)） |
| `touch_up` 后没有抬起事件 | `touch_up` 只发 `button(released)`，若 `touch_down` 没成功，抬起也无意义 |

### 转视角没变化

先分清走的是哪条路：

```bash
# 相对移动：日志里应有 PostRelativeMove，且耗时约 0ms
grep -a "PostRelativeMove" maafw.log | tail -3

# 绝对移动：走 Swipe 节点，日志里是 node 执行记录
```

| 现象 | 结论 |
| --- | --- |
| 有 `PostRelativeMove`、页面无指针事件 | 相对移动不可用（见 [01 已知缺口 1](01-控制器能力与限制.md#已知缺口)） |
| 相对移动一行日志都没有 | 说明节点没执行到，检查 `resource_linux` 是否把该节点 remap 成了 `DoNothing` 或 `Custom` |
| 有事件、`movementX = 0` | 客户端按位置差算位移，检查是否有中间层改了指针位置 |

### 画面不动 / 黑帧 / 全是纯色

```bash
# 用官方工具对照：grim 与 Wlr 截图走同一个协议
grim /tmp/grim.png && python3 -c "from PIL import Image; im=Image.open('/tmp/grim.png'); print(im.size, im.mode)"

# 我们的截图
python3 -c "from maa.controller import LinuxController; ...; print(ctrl.post_screencap().wait().get().shape)"
```

| 对照结果 | 结论 |
| --- | --- |
| grim 正常、我们黑帧 | 控制器连的 socket 不是同一个合成器实例 |
| 两者都黑 | 合成器没在输出，或 Chrome 没在渲染（检查 `--headless`、GPU 参数） |
| 两者尺寸不同 | `display_*` 缩放被设置了，或抓的不是同一个 output |

### 按键错位（例如想按 Esc 却触发别的键）

**唯一原因**：键码空间不一致。Linux 控制器默认 `use_win32_vk_code: false`，即把传入的 `key` 当 evdev 扫描码；而 pipeline 若按 Win32 VK 写（Esc = 27），就会被当成另一个键。

```jsonc
"use_win32_vk_code": true   // pipeline 用 VK 写时必须设
```

判据：发 `key_down(27)`，页面应收到 `code = "Escape"`。若收到 `BracketRight` 之类，就是这个原因。

### `resolution` 返回 `(0, 0)`

不是配置错误，是 API 未实现（同 `start_app`）。用截图尺寸代替：

```python
h, w = ctrl.post_screencap().wait().get().shape[:2]
```

### 启动游戏失败（`start_app`）

`LinuxControlUnitMgr::start_app()` 是 `// TODO` + `return false`。任何依赖 `StartApp` 动作的 pipeline 在 Linux 上都会失败。改用宿主/预任务在框架外拉起。

### 多指手势无效

Wlr / UInput 输入没有多点触控，`contact` 只映射左/右/中键（见 [01](01-控制器能力与限制.md#2-鼠标型输入下-contact-不是手指编号)）。需要真多指只能走 Libei。

## 通用工具

| 工具 | 用途 |
| --- | --- |
| `grim` | 同协议截图对照，判断「画面」问题 |
| `wev` | 观察 Wayland 客户端收到的事件（本机或页面侧代理） |
| `MAA_DEBUG=1` / `maafw.log` | 每条 Controller API 的 enter/leave 与错误 |
| `pgrep -a sway` | 确认合成器实例与 socket 对应 |
| `swaymsg -t get_outputs` | 确认输出尺寸与缩放 |

## 定位口诀

> **先分清是哪一层没收到**：请求发出去了吗 → 合成器收到了吗 → 浏览器收到了吗 → 页面逻辑用了吗。

四层各自的判据：

| 层 | 判据 |
| --- | --- |
| 框架 | `maafw.log` 有没有这条 API |
| 合成器 | 指针位置是否变化（`motion_absolute` 生效说明这一层通） |
| 浏览器 | 页面是否收到 `pointer*` / `key*` / `wheel` 事件 |
| 页面逻辑 | 事件里的字段是否满足页面要求（`movementX`、`button`、`code`） |
