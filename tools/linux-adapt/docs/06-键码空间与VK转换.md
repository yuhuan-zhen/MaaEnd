# 06 · 键码空间：同一个数字，三种解释

这篇只讲一件事：**`"key": 70` 到底是哪个键**。

看起来是个小问题，但它是 Linux 适配里最隐蔽的坑——不报错、不失败、日志干净，只是游戏里按什么都没反应。

## 0 · 一句话结论

MaaEnd 的 pipeline 里所有按键数字都是 **Win32 Virtual-Key**；Linux 控制器默认把它们当 **evdev 扫描码**读；必须显式设 `use_win32_vk_code: true` 才会转换。

## 1 · 症状长什么样

三个特征，缺一不可地指向这个坑：

| 现象 | 为什么 |
| --- | --- |
| 节点全部 `Succeeded` | `ClickKey` 只返回「事件已发给合成器」，不代表游戏收到了正确的键 |
| 日志无任何 error/warn | 转换是静默的：不认识的键返回 0，发出去就是无效键码 |
| 游戏里完全没反应 | 键到达了，但按的是 ScrollLock / `]` / 小键盘数字 |

对比一下「真正失败」的样子：`input_ is null`、`relative_move is not supported` 这类都会在 `maa.log` 里留一行 `LogError`。这个坑**一行都不留**。

## 2 · 三种编号

同一台 Linux 上，同一个物理键至少有三套编号：

| 键 | Win32 VK | evdev `KEY_*` | xkb keycode |
| --- | --- | --- | --- |
| Esc | **27** (`0x1B`) | **1** | 9 |
| F | **70** (`0x46`) | 33 | 41 |
| 空格 | **32** (`0x20`) | 57 | 65 |
| M | **77** (`0x4D`) | 50 | 58 |
| A | **65** (`0x41`) | 30 | 38 |
| `]` | 221 (`0xDD`) | **27** | 35 |

关系：

```text
xkb keycode = evdev code + 8        （固定偏移，Wayland 协议层用 xkb keycode）
Win32 VK    = 与上面两者无任何换算关系（0x00–0xFF 里另起一套）
```

关键点：**27 在两套体系里都是合法值，但指向两个不同的键**。所以「传错了」不会越界、不会崩溃，只会安静地按错。

## 3 · 事实核查：MaaEnd 存的是 VK

不能只凭印象。把 MaaEnd `assets/resource/pipeline/` 下所有 `"key": <n>` 抽出来统计（2026-10-25 实测）：

总计 **79 处引用，24 个不同键值**。按两种解释分别查表：

| --- | --- | --- | --- |

| 18 | 10 | `KEY_LEFTALT` ✅ | `KEY_E` ❌ |

| 83 | 6 | `KEY_S` ✅ | `KEY_KPDOT` ❌ |
| 16 | 4 | `KEY_LEFTSHIFT` ✅ | `KEY_Q` ❌ |
| 87 | 4 | `KEY_W` ✅ | `KEY_F11` ❌ |
| 164 | 4 | `KEY_LEFTALT`（VK_LMENU）✅ | `KEY_PLAYPAUSE` ❌ |
| 65 | 3 | `KEY_A` ✅ | `KEY_F7` ❌ |

**结论无可争议**：按 VK 读，24 个值全是游戏里会用到的键（Esc、Alt、F、W、A、S、D、R、E、Shift、数字键）；按 evdev 直读，全是不可能用到的键（ScrollLock、小键盘、光盘弹出、Q 却当成 Shift）。


70 = `0x46` = `VK_F`，注释与 VK 解读完全一致。

## 4 · 框架里唯一的开关

`source/MaaLinuxControlUnit/Manager/LinuxControlUnitMgr.cpp:322`：

```cpp
int LinuxControlUnitMgr::translate_key(int key) const
{
    if (!config_.use_win32_vk_code) {
        return key;              // 默认：原样透传 → 被当作 evdev 扫描码
    }

    return vk_to_evdev(key);     // 开了：查表 VK → evdev
}
```

**就这么一个 if。** 整个「VK ↔ evdev」的适配面只有这一个判断，没有第二处。

配置来源 `config_json`（`MaaLinuxControllerCreate` 的唯一参数），必填与选填：

| 字段 | 默认 | 作用 |
| --- | --- | --- |
| `screencap_method` | 无（必填） | `None=0`、`Wlr=1`、`ExtImage=2`、`PipeWire=4` |
| `input_method` | 无（必填） | `None=0`、`Wlr=1`、`UInput=2`、`Libei=4` |
| `wlr_socket_path` | 无（选 Wlr 时必填） | Wayland socket |
| `use_win32_vk_code` | **`false`** | 见上 |

枚举取值逐字来自 `/opt/maafw/extract/include/MaaFramework/MaaDef.h:489-511`。

### 为什么默认是 `false`

因为「Linux 原生开发者」用 evdev 更直觉：他写 `MaaLinuxController` 自己的程序时，想按 `KEY_F`（33）就写 33。

默认值服务的是这些人，代价是所有 Windows 出身的上层框架（MaaEnd 就是）都必须显式打开。

### 这条开关的历史

它比 `config_json` 更早存在。`MaaFramework.cpp:264` 还留着旧的 C 参数式入口：

```c
MaaController* MaaWlRootsControllerCreate(const char* wlr_socket_path, MaaBool use_win32_vk_code);
```

后来统一成 JSON 化入口后，同一个语义被搬进 `config_json` 的 `use_win32_vk_code` 字段。KWin 入口（`:308`）也带同名参数。**这说明该字段不是可选装饰，而是从第一版就有的必需语义**。

## 5 · 两条输入路径：`click_key` 不转换

这是最容易忽略的一处不对称。`LinuxControlUnitMgr` 里：

| 方法 | 行 | 是否 `translate_key` |
| --- | --- | --- |
| `click_key` | 185 | **否** |
| `key_down` | 205 | 是（`:211`） |
| `key_up` | 216 | 是（`:222`） |

```cpp
bool LinuxControlUnitMgr::click_key(int key)
{
    return input_->click_key(key);        // ← 原样交给插件，不转换
}

bool LinuxControlUnitMgr::key_down(int key)
{
    const int evdev_key = translate_key(key);
    return input_->key_down(evdev_key);   // ← 转换后才交
}
```

那为什么实际不会出问题？因为**四个 Linux 输入插件全都申报了「用 key_down/key_up 代替 click_key」这个 feature 位**：

| 插件 | `get_features()` 位置 | 申报的位 |
| --- | --- | --- |
| `WlrInput` | `WlrInput.cpp:23` | 两个位都有 |
| `UInput` | `UInput.cpp:71` | 两个位都有 |
| `EiInput` | `EiInput.cpp:25` | 两个位都有 |
| `NoneInput` | `NoneInput.cpp:6` | 两个位都有 |

而执行器看到这一位就会拆成 down + 50ms + up（`ControllerAgent.cpp` 的 `handle_click_key`）：

```cpp
    bool use_key_down_up = control_unit_->get_features() & MaaControllerFeature_UseKeyboardDownAndUpInsteadOfClick;
    ...
        if (use_key_down_up) {
            ret &= control_unit_->key_down(keycode);      // ← translate_key 生效
            std::this_thread::sleep_for(std::chrono::milliseconds(50));
            ret &= release_key_if_held(keycode);
        }
        else {
            ret &= control_unit_->click_key(keycode);     // ← 会绕过转换
        }
```

所以完整链路是：

```text
pipeline "key": 70
  → ControllerAgent::handle_click_key（feature 位为真 → 拆成 down/up）
    → LinuxControlUnitMgr::key_down(70)
      → translate_key(70)  →  查表  →  33 (KEY_F)
        → WlrInput::key_down → zwp_virtual_keyboard_v1_key(xkb 41)
```

**但要记住**：`else` 那条分支今天是死代码，**将来任何一个新输入插件忘了申报这个位，`ClickKey` 就会绕过 `translate_key`**——症状还是「静默按错」。所以自研控制器时，这条等价逻辑必须自己保证。

## 6 · 转换表本身（`Input/VkToEvdev.h`，207 行）

表结构就是 `std::array<int, 256>`，索引是 VK，值是 evdev：

```cpp
    table[0x1B] = KEY_ESC;       // VK_ESCAPE     ← 27 → 1
    table[0x20] = KEY_SPACE;     // VK_SPACE      ← 32 → 57
    table[0x46] = KEY_F;         // VK_F          ← 70 → 33
```

作者在头部写明了三条约定（`VkToEvdev.h:16-19`）：

| 约定 | 含义 |
| --- | --- |
| `VK_SHIFT` / `VK_CONTROL` / `VK_MENU` 默认映射到**左**变体 | 只写 16/17/18 时按左 Shift/Ctrl/Alt 处理 |
| 显式的 `0xA0..0xA5` 映射到各自的左右键 | 164 = `VK_LMENU` → `KEY_LEFTALT`；160 = `VK_LSHIFT` → `KEY_LEFTSHIFT` |
| OEM 标点按 **US 布局** | 中文/日文键盘上的 `;` `'` `[` `]` 可能与人预期不同 |

### 未覆盖的键会怎样

```cpp
// Returns the evdev key code for a given Win32 VK code, or 0 if no mapping exists.
inline int vk_to_evdev(int vk)
{
    if (vk < 0 || vk >= static_cast<int>(kVkToEvdevTable.size())) {
        return 0;
    }
    return kVkToEvdevTable[vk];
}
```

返回 `0`，而 `0` 在 evdev 里是 `KEY_RESERVED`。发出去等于发了个无效键——**不崩溃、不报错、不生效**。这就是第 1 节那三个特征的来源。

## 7 · 我们自己的实现（CustomController）不走这段代码

我们的云网页控制器是 `MaaCustomControllerCreate`，**没有 `config_json`，也就不存在 `use_win32_vk_code`**。等价工作必须自己完成：

| 层 | 上游（`MaaLinuxController`） | 我们（`cdp_controller.py`） |
| --- | --- | --- |
| 谁做转换 | `LinuxControlUnitMgr::translate_key` | `_vk_to_dom_code()` 手写表 |
| 转到什么 | evdev `KEY_*` | DOM `code`（`"Escape"`、`"KeyM"`） |
| 开关 | `use_win32_vk_code: true` | 无开关，**恒定按 VK 解释** |
| 未覆盖的键 | 返回 0 → 静默无效 | **显式返回 False 并报错** |

我们的做法在这一点上比上游更严：上游对未覆盖键静默发 0，我们直接失败。理由是云网页只有 DOM `code` 一条路，静默失败会让排查无限变长。

自检证据（`evidence/selfcheck.log`，2026-10-24 10:52）：

```text
keys[-2:] == ["Escape", "KeyM"]
```

即 VK 27 → `Escape`、VK 77 → `KeyM`，与 Win32 语义一致。

## 8 · 怎么验证（三种方法，从便宜到彻底）

### 方法 A：看转换结果对不对（1 分钟）

```bash
wsl.exe -d Ubuntu-24.04 -- bash -c 'grep -nE "0x1B|0x46|0x20" /tmp/VkToEvdev.h'
```

期望：`0x1B → KEY_ESC`、`0x46 → KEY_F`、`0x20 → KEY_SPACE`。

### 方法 B：看合成器实际收到什么（5 分钟，最直观）

在 WSL 的 sway 里起 `wev`（wayland event viewer），然后发一个按键：

```bash
# 终端 1
wev | grep -A3 "key"
# 终端 2：发 VK 70（应为 F）
```

`wev` 打出 `keysym: f` 就对了；打出 `Scroll_Lock` 说明 `use_win32_vk_code` 没开。

### 方法 C：端到端（游戏里）

选一个「有明确反馈、可回退」的键：MaaEnd 的 `AutoCollectClick`（`key: 70`，F 交互）最合适——按 F 会有交互提示或拾取动作，肉眼可判。

跑一次，看游戏是否响应；不响应而日志全绿，就是这个坑。

## 9 · 检查清单

给自己的实现或代码评审用：

- [ ] 控制器创建时显式写了 `use_win32_vk_code: true`（不是靠默认值）
- [ ] 知道本项目 pipeline 的键值来源（Win32 VK），没有在中途做过二次转换
- [ ] 自研控制器里 VK → 目标键码只有**一处**映射表，且未覆盖的键**显式失败**
- [ ] 若新增了 `InputBase` 实现，`get_features()` 申报了 `UseKeyboardDownAndUpInsteadOfClick`
- [ ] 自检里有一条断言覆盖「Escape」与一个普通字母键（例：`KeyM`）

## 10 · 自测 6 题

1. pipeline 写 `"key": 32`，`use_win32_vk_code` 默认 false 时，游戏收到的是哪个键？
2. 为什么这个坑不会在日志里留下痕迹？
3. `translate_key` 在哪个文件哪一行？它是 `LinuxControlUnitMgr` 的成员还是自由函数？
4. `click_key` 为什么不走 `translate_key` 也不出问题？
5. `VkToEvdev.h` 对未覆盖的 VK 返回什么？在 evdev 里这个值是什么含义？
6. 我们自己的 CDP 控制器没有 `config_json`，那「始终按 VK 解释」这件事是靠什么保证的？

<details>
<summary>答案</summary>

1. `KEY_M`。evdev 32 是 `KEY_M`，不是空格（空格是 57）。
2. 因为整条路径只有一处 `if`，且未覆盖的键返回 0（`KEY_RESERVED`），发出去既不崩溃也不报错；`ClickKey` 的返回值只表示「事件已发」。
3. `source/MaaLinuxControlUnit/Manager/LinuxControlUnitMgr.cpp:322`，是 `LinuxControlUnitMgr` 的私有成员函数（`const`）。
4. 因为四个 Linux 输入插件都申报了 `UseKeyboardDownAndUpInsteadOfClick`，执行器（`ControllerAgent::handle_click_key`）直接改走 `key_down`/`key_up`，那两条路径会转换。`click_key` 分支今天是死代码。
5. 返回 `0`；evdev 的 0 是 `KEY_RESERVED`，等于发了个无效键。
6. 靠我们自己的 `_vk_to_dom_code()` 手写表恒定按 VK 解释，并且未覆盖的键显式返回失败。

</details>

## 附录 · 统计脚本说明

仓库里的 `keycensus.py` 就是下面这段（带类型标注与参数化），核心逻辑：

```python
import re, pathlib, collections

VK = pathlib.Path("/tmp/VkToEvdev.h").read_text(encoding="utf-8", errors="ignore")
inv = {int(m.group(1), 16): m.group(2)
       for m in re.finditer(r"table\[(0x[0-9A-Fa-f]+)\]\s*=\s*(KEY_[A-Z0-9_]+)", VK)}

EV = pathlib.Path("/usr/include/linux/input-event-codes.h").read_text(encoding="utf-8", errors="ignore")
code2name = {}
for m in re.finditer(r"#define\s+(KEY_[A-Z0-9_]+)\s+(0x[0-9a-fA-F]+|\d+)", EV):
    v = int(m.group(2), 16) if m.group(2).startswith("0x") else int(m.group(2))
    code2name.setdefault(v, m.group(1))

root = pathlib.Path("/mnt/d/桌面/常用/面向MMAEND项目/MaaEnd-linux-adapt/assets/resource/pipeline")
keys = collections.Counter()
for f in root.rglob("*.json"):
    txt = f.read_text(encoding="utf-8", errors="ignore")
    for m in re.finditer(r'"key"\s*:\s*(\[[^\]]*\]|\d+)', txt):
        for n in (int(x) for x in re.findall(r"-?\d+", m.group(1))):
            if 0 < n < 256:
                keys[n] += 1

for n, c in keys.most_common():
    print(n, c, inv.get(n, "（无映射）"), code2name.get(n, "?"))
```
