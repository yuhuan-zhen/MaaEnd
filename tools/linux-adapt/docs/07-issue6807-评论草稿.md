Linux 侧补充三组实测，加一条资源层结论。

### 1. 取帧延迟（对应风险 1）

环境：WSL2 Ubuntu 24.04 / WSLg / 无 GPU 直通（软件渲染）/ 1280×720。

| 路径 | 编码 | median | p95 | 备注 |
| --- | --- | --- | --- | --- |
| Wlr screencopy（`zwlr_screencopy_manager_v1`） | 无，BGR 直出 | **16.13 ms** | 16.28 ms | 与 `grim` 抓帧 NCC = 1.0；静止 20 帧标准差 0.0 |
| CDP canvas → `toDataURL` | PNG | **103–154 ms** | — | 四次独立批次 |

一个口径提醒：#6696 里那个 190 ms 是 **1080p JPEG**，上表是 **720p PNG**，两者不能直接比。1080p 像素量是 720p 的 2.25 倍，JPEG 编码又比 PNG 便宜得多，按像素折算 JPEG@720p 大致落在 50–90 ms（**未实测**）。

也就是说：如果 `frame.source = video` 能输出 JPEG，取帧可能落在 10–15 fps 区间，比 190 ms 给人的印象好不少。但 **JPEG 有损，对模板匹配命中率的影响必须先测再定**，这是必验项，不是可选优化。

### 2. 两个客户端同时连（对应风险 3）

`--remote-debugging-pipe`（控制器输入）+ `127.0.0.1:9334`（只读探测）同时访问同一页面，未冲突。

**但没测两个客户端同时发输入时的串扰**，这一项仍是未验证。

### 3. `resource_linux` 挂不挂（4.4 那条待确认）

建议**不挂**。该层只有两个文件：

- `Common/Private/CharacterController/Action.json`：把 `__CharacterControllerDeltaSwipeAction` remap 成 `Custom → RelativeMove`，同时把 ClickCenter / AltKeyDown / AltKeyUp 设为 `DoNothing`。实测这条路在 Linux 上 `PostRelativeMove` 返回成功（`leave, 0ms`）但画面零变化（相关系数 0.94–1.0），同链路 base 的 hover Swipe 生效（NCC 0.247）。挂上它会一次性打断 yaw / pitch / MoveToTarget / NotFound。
- `GameLauncher.json`：Linux 启动器适配，对云网页无用。

云游戏画面来自云端，与 PC 端在 Proton 下的渲染差异无关，这层对 `resource_cloud_web` 没有收益。

### 4. 两个问题

- `frame.source = video` 走 `Runtime.evaluate` 返回 base64，还是 `Page.captureScreenshot` + `clip`？如果是前者，`frame` 段是否考虑暴露编码格式与质量参数？
- `relative_move.max_step = 127` 的依据是什么？我们只在**假页面**上验证了「分片后 `movementX` 合计等于请求值」（200 → 200），**没在真页面验证 >127 是否被截断**；目前这条依据是 #6746 `CloudBridge.cpp:368-372` 的注释（串流 SDK 把 `movementX/Y` 截成 8 位符号幅度）。如果另有实测来源，值得记进 `2.4-控制方式说明.md`。
