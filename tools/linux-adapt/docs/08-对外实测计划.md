## 0. 回复策略：先给方法，再给数字

维护者评价一份数据，看的不是结论大小，而是**能不能复现**。所以回复顺序固定为：

1. **已测的**（标「实测」，附条件与样本量）
2. **要测的**（标「计划中」，附方法与判据）
3. **不能测的**（标「不可得」，附原因）

三档标注是我们已经在 `docs/` 里坚持的写法，对外继续用。**绝不把推算写成实测**——这是唯一会毁掉可信度的做法。

## 1. 通用证据规范（先立规矩，再谈测什么）

### 1.1 每条数据必须附带的六项环境

| 项 | 取法 |
| --- | --- |
| OS / 内核 | `uname -a`、`lsb_release -a` |
| 是否 WSL | `grep -i microsoft /proc/version` |
| 渲染器 | `glxinfo -B \| grep -i renderer`、`chrome://gpu` 的 GL_RENDERER 行 |
| CPU | `lscpu \| grep "Model name"` |
| 合成器 / 浏览器版本 | `sway --version`、`google-chrome --version` |
| 视口 / DSF / headless | 视口 1280×720、`deviceScaleFactor`、`--headless=new` 与否 |

`glxinfo` 需要 `mesa-utils`；没装就用 `chrome://gpu` 的文本导出，别省这一项。

### 1.2 MaaEnd 仓库本身的硬约束（引用，不是自创）

| 约束 | 出处 | 对测量的影响 |
| --- | --- | --- |
| 所有坐标与识别图以 **720p（1280×720）** 为基准 | `AGENTS.md`「Pipeline 低代码规范」 | 延迟必须在 1280×720 下测，1080p 数字只作对照 |
| 识别遵循「识别 → 操作 → 再识别」，**禁止盲目 `pre_delay` / `post_delay`** | `AGENTS.md` 同上 | 不能靠加延迟掩盖取帧慢，只能报真实耗时 |
| 节点测试用「静态图 + 期望命中」的形式（`tests/**/*.json`） | `docs/zh_cn/developers/node-testing.md` | 识别回归可以不依赖显示器，JPEG 影响可以 CI 化验证 |
| 新增/导入识别测试图要脱敏、按约定命名放 `tests/` | `.agents/skills/maaend-test-image/SKILL.md` | 若要补测试图，走这套流程，不自己造目录 |
| **`pnpm check` / `pnpm test` 默认交给 CI**，本地只在改动 `tests/**` 或用户明确要求时跑 | `AGENTS.md`「验证按需」 | 我们只在验证 JPEG 影响时临时跑，不把它当日常 |
| 代码风格与格式化以 `coding-standards.md` / `.prettierrc` 为准 | `AGENTS.md` 第 6 节 | 导出脚本也要按格式提交 |

### 1.3 六条判据：什么样的数据算「有说服力」

1. **样本量 ≥ 30 帧，丢弃预热帧**（前 5 帧），报 median / p95 / min / max，不只报一个均值
2. **≥ 3 个独立批次**（重新启动浏览器与控制器），批间差异要报出来——只有一个批次的数字不算数
3. **必须有负对照**：例如测「JPEG 影响」要同时报 PNG 原图的命中率；测「`resource_linux` 破坏性」要有不加载该层的对照组
4. **变量单一**：一次只改一个（编码格式 / 分辨率 / headless），同时改两个就说不清是谁造成的
5. **可复现命令 + 原始输出**：给出一条能直接跑的命令，并把 stdout、原始 JSON、截帧落盘路径写进回复（放 `evidence-*/`，不进 git）
6. **换算要写明是换算**：由 1080p 推 720p、由 PNG 推 JPEG，都要标「未实测」

### 1.4 五种会被当成不可信的做法（明确避免）

| 反模式 | 为什么致命 |
| --- | --- |
| 只报一个数（如「约 110 ms」）不给分布 | 无法判断是常态还是偶发 |
| 混用口径（1080p JPEG 与 720p PNG 并排比） | 一眼被抓，之后所有数字都被怀疑 |
| 用「画面看起来转了」当结论 | 无法量化，且受相机平滑影响 |
| 只在一台 WSL 上测却写成「Linux 上」 | 过度外推 |
| 结论先行再找数 | 只要被问一句「换台机器呢」就站不住 |

## 2. 七项测试（按对外价值排序）

每项含：要回答什么 → 怎么测 → 判据 → 谁动手。

### T1 · 取帧延迟与编码代价（最高优先级）

**要回答**：`frame.source=video` 的取帧在不同编码下各是多少？190 ms 到底是什么口径？

**怎么测**（四条路径，同一页面同一浏览器，逐条单变量）：

| 路径 | 调用 |
| --- | --- |
| P1 | `Page.captureScreenshot`（PNG，全视口） |
| P2 | `Runtime.evaluate` → `canvas.toDataURL('image/png')` |
| P3 | `Runtime.evaluate` → `canvas.toDataURL('image/jpeg', q)`，q = 1.0 / 0.9 / 0.8 |
| P4 | `Page.captureScreenshot`（`format=jpeg`，`quality` 同上） |

每条 30 帧、丢弃前 5 帧、跑 3 个批次。同时记录**每帧 base64 字节数**——这是解释差异的关键变量，可以直接算出 `字节数 × fps = 所需带宽`，让维护者自己复核。

**判据**：报 median / p95 / min / max + 三批次差异 + 每帧字节数。若 JPEG@720p 落在 50–90 ms，则「风险 1」的结论要改；若落在 150 ms 以上，则我们的推算错了，要认。

**谁动手**：我写采集脚本（Python，工具层），你负责跑并确认机器状态（是否有其他负载）。

**已有**：720p PNG 103–154 ms（4 批次）、Wlr 16.13 ms（20 帧）→ 本次只是补 JPEG 与 1080p 对照、补字节数。

### T2 · JPEG 对识别的影响（必验项，最容易被质疑）

**要回答**：有损编码会不会让模板匹配 / OCR / 颜色识别掉命中？

**怎么测**（用仓库自己的验收口径，不另造标准）：

1. 从 `tests/**/*.json` 里挑 5 组现有用例：小图标、OCR、颜色识别、多目标、边缘 ROI 各一
2. 原图跑一次本地 `pnpm test`，记录每组 `hits` 与 score
3. 把用例图用 JPEG q=95/90/80 重编码后再转回 PNG（模拟串流编码损失），放进**临时副本**目录
4. 重跑，逐组对比：命中 / 未命中 / score 变化

**判据**：不是「看起来还行」，而是逐组列出 hit 与 score；只要有一组从命中变未命中，就要在回复里写明「JPEG 会破坏 X 类识别」。

**注意**：按 `AGENTS.md`「为验证而生成临时测试文件，验证完成后删除」，临时副本不进 git；要长期保留就用 `maaend-test-image` 的流程正式提交。

**谁动手**：我准备用例副本与对比脚本，你跑 `pnpm test`（需要 pnpm 与测试集子模块）。

### T3 · 两个 CDP 客户端并发（风险 3）

**要回答**：两个客户端同时连同一页面，会不会互相干扰？

**怎么测**：A 用 `--remote-debugging-pipe` 持续发输入，B 用端口客户端高频截图，分三组：

| 组 | 内容 |
| --- | --- |
| 基线 | 只有 A 发输入，记录每次输入到页面事件的时间戳 |
| 并发截图 | A 发输入的同时 B 以 10 fps 截图，看 A 的延迟是否上升、是否丢事件 |
| 双向输入 | A、B 同时发 click，看页面是否收到两次（串扰） |

**判据**：给出「输入延迟 基线 vs 并发」两组分布；双向输入必须给出「收到 1 次还是 2 次」的确定结论。

**已有**：只验证了「能并发连接、未明显冲突」。**串扰未测**，这条必须补。

**谁动手**：我写脚本，你跑。

### T4 · `resource_linux` 的破坏性（对应 4.4 那条待确认）

**要回答**：`resource_cloud_web` 要不要挂 `resource_linux`？

**怎么测**（对照实验，固定场地与朝向）：

| 组 | 配置 | 动作 |
| --- | --- | --- |
| A | 不挂 | `YawDelta 90`（dx=180）× 4 |
| B | 挂 | 同上 |

每组 3 次重复，每次重新 connect。记录前后帧 NCC、以及画面是否发生位移。

**判据**：A 组应有可测画面变化（已知 NCC 0.247），B 组若相关系数 0.94–1.0（≈没动），即证明 remap 打断转视角。**两组都必须报，不能只报 B。**

**已有**：A 有（NCC 0.247）；B 有（0.94–1.0）。**缺的是同场同朝向的配对测量**——现在这两组不是同一时刻测的，严格说不能直接比。这条要补。

**谁动手**：需要进游戏（云游戏会话），由你操作站位，我发动作与抓帧。

### T5 · `relative_move` 的 >127 行为（当前最弱的一环）

**要回答**：单次相对移动超过 127 px 会不会被截断？

**怎么测**（读页面收到的值，不看画面）：

1. 在页面注入记录器，把每次 `mousemove` 的 `movementX/movementY` 存进 `window.__log`
2. 依次发 dx = 60 / 120 / 127 / 128 / 200 / 254 / 300 / 360，每个值重复 5 次
3. 用 `Runtime.evaluate` 读回 `window.__log`，比对「请求值 vs 累计收到值」

**判据**：给出 8 个请求值 × 5 次的对照表。出现「请求 200、实收 127」即证明确有截断；全部相等则证明 127 这个上限在当前环境不成立——**两种结果都要如实报**。

**这条最有价值**：它是二值可判的，且直接决定 `relative_move.max_step` 该写多少。

**谁动手**：我写脚本，你跑（可以在探针页跑，不必进游戏）。

### T6 · Chrome 启动参数清单（4.1）

**要回答**：Linux 侧拉起浏览器需要哪些参数、各自解决什么。

**怎么测**：不是测数值，是做**单参数消融**：每条参数去掉后观察可观察症状。

| 参数 | 去掉后的预期症状 |
| --- | --- |
| `--app=<url>` | 出现地址栏与标签栏，视口与 UI 位置变化 |
| `--remote-debugging-port=0` | 拿不到调试端口，`endpoint_file` 无从生成 |
| `--user-data-dir=<独立>` | 复用默认 profile，登录态与实例互相污染 |
| 防节流那组（后台标签节流 / 遮挡计算） | 窗口失焦后帧率下降、截图卡顿 |
| `--force-device-scale-factor=1` | DSF 随系统变，坐标与模板全部失配 |

**判据**：每条给出「删掉后看到什么」的具体现象，而不是「这条很重要」。

**谁动手**：我列清单，你按条验证（多数可以肉眼确认）。

## 4. 可直接贴的回复（第一版：只报已测 + 宣布计划）

> 下面这段可以现在发，它不承诺任何未测数字，只报方法与本机已得结果。

---

Linux 侧的情况我先同步一下，数字都带条件，方法也写清楚，方便你们复核。

**已测（WSL2 / WSLg / 无 GPU 直通 / 软件渲染 / 1280×720）**

| 路径 | 编码 | median | p95 |
| --- | --- | --- | --- |
| Wlr screencopy | 无（BGR 直出） | 16.13 ms | 16.28 ms |
| CDP canvas → `toDataURL` | PNG | 103–154 ms（4 批次） | — |

一个口径问题：#6696 里的 190 ms 是 **1080p JPEG**，上表是 **720p PNG**，两者不能直接比。按像素量折算，JPEG@720p 大致在 50–90 ms（**这是换算，未实测**）。

**接下来我会补测以下四项，方法先放这里，结果出来后更新本楼：**

1. 同一页面下四条取帧路径的耗时与**每帧 base64 字节数**（PNG / JPEG q=1.0 / 0.9 / 0.8，各 30 帧 × 3 批次）——字节数比耗时更能说明瓶颈，也能直接算出需要多少带宽
2. `relative_move` 单次超过 127 px 时页面实际收到的 `movementX`（读页面记录，而不是看画面转了多少）。`max_step=127` 目前依据是 #6746 的注释，我想把它变成实测值
3. 两个 CDP 客户端并发时：输入延迟是否上升、双向同时输入是否串扰
4. `resource_linux` 与不加载它的配对对照（同一场地同一朝向，各 3 次）

另外一条现在就能答的：**`resource_cloud_web` 建议不挂 `resource_linux`**。那层把 `__CharacterControllerDeltaSwipeAction` remap 成 `Custom → RelativeMove`，实测 `PostRelativeMove` 返回成功但画面无变化，同链路 base 的 hover Swipe 生效（NCC 0.247 / 0.94–1.0 两组）。挂上会打断 yaw、pitch、MoveToTarget、NotFound。
